# Upload / Media Domain

Status: authoritative
Last reviewed: 2026-09-15
Implementation status: implemented (Phase 3 MVP — temporary photos + private storage; audio via transcription endpoint only)

## 1. Purpose

This domain owns Houston's file and media lifecycle for operational workflows: temporary upload handling, server-side validation, linking media to the correct parent resource, authorized access, and cleanup.

It does not own Observation submission validity, AI transcription behavior, privacy policy details, or RBAC policy details. Those remain in the Observation, AI, Security / RGPD, and RBAC / Permissions domains.

## 2. MVP Scope

- Optional photos attached to Observations.
- MVP allows up to 3 photos per Observation.
- Temporary uploads before or during Observation submit.
- Server-side validation before a file is accepted or linked.
- Linking valid media to the submitted Observation.
- Cleanup of unlinked or expired uploads.
- Private-by-default media access through authorized backend flows.
- Temporary audio used only to produce editable transcription text.
- Deletion of transcription audio after transcription success or final failure.
- No image input sent to AI in MVP.

## 3. Out of Scope

- Public media galleries, public sharing links, or publicly reachable media URLs (chat media stays establishment- and conversation-scoped).
- Public media galleries, public sharing links, or publicly reachable media URLs.
- Arbitrary file manager behavior.
- Document, PDF, or video upload unless later validated.
- Long-lived audio storage.
- OCR, image understanding, or image-to-AI workflow.
- Direct browser-to-storage upload for Observation photos (multipart remains). Chat attachments use a dedicated private bucket and presigned PUT.
- Media editing, cropping, or library management workflow.
- Cross-resource media reuse outside validated parent-resource rules.

## 4. Core Invariants

- Files are untrusted input.
- Backend validation is authoritative for file type, size, ownership, and allowed parent context.
- Observation photos are normalized on temporary upload before storage: EXIF orientation is applied then stripped, pixels are converted to sRGB when a usable ICC profile is present, the long edge is capped at 1600 px without upscaling, and the file is re-encoded as JPEG (quality 82, optimize + progressive) or PNG when alpha is actually useful. Stored `content_type`, `stored_extension`, and `size_bytes` describe that **principal** file. The same request also encodes a JPEG thumbnail (long edge 320 px, quality 72, optimize, not progressive; PNG alpha flattened onto white). Principal and thumbnail objects are persisted atomically with the `TemporaryUpload` row: encode both in memory first; if either storage write or the DB save fails, already-written keys are deleted and no validated row remains. There is no lazy thumbnail write on GET. Thumb keys are derived (`{id}.jpg` / `{id}.png` → `{id}.thumb.jpg`). Cleanup and delete remove both objects.
- Observation photo reads go through the Houston preview gate (`preview_url` / `thumbnail_url`, same token, `variant=full|thumbnail`). After authorization, production S3 returns 302 to a short-lived private GET; filesystem (dev/CI) streams `FileResponse`. The JSON never contains a bucket URL. `Referrer-Policy: no-referrer` applies to the Houston response.
- Cache / revocation uses two clocks, not one absolute cutoff: **C** (60 s) is the maximum delay before the next Houston gate check (`Cache-Control: private, max-age=60, must-revalidate` on the Houston response, often a 302). **P** (120 s) is how long an already-issued S3 URL remains acceptable to the bucket. After archive, Houston 404s once **C** expires; a `Location` already delivered can still work until **P** unless the storage object was deleted. The presign sets `ResponseCacheControl=private, max-age=120, must-revalidate` so the bucket GET cache is not longer than **P**. Preview tokens reuse the existing signer (payload `establishment_id:media_id`, `max_age` **T**=3600 s) with a bucketed timestamp (**W**=60 s) so serializations in the same window share a token. Cache is never `public` / `immutable` / `s-maxage`.
- Production private media is the S3 bucket (`HOUSTON_PRIVATE_MEDIA_BACKEND=s3`). Filesystem storage is the local/test default. Do not treat an `api-web` volume as production media truth.
- Client-provided MIME type, filename, and metadata are hints only, never business authority.
- Storage keys must be generated by the backend and must not rely on raw user filenames.
- Media is private by default and remains establishment-scoped through its parent resource.
- Observation photos are optional, but a photo alone must not create a valid Observation.
- Audio is transcription-only in MVP and must not become persistent Observation media.
- Images are not sent to AI in MVP.
- Signals may surface media only through authorized linked Observation context; media must not become standalone Signal-owned content unless later validated.
- Media content must not appear in logs, notifications, realtime payloads, or durable frontend storage.
- Upload success does not mean Observation submit success.
- Orphan uploads must be cleaned up.
- Accepted **input** image formats are `jpeg`, `jpg`, `png`, `webp`, and `heic`/`heif` when backend validation can decode them. Durable Observation photos are stored as normalized JPEG or PNG.

## 5. Main Objects

- `ChatUpload` / `ChatMessageAttachment`
  - Chat attachments live in the dedicated `chat-attachement` bucket (`HOUSTON_CHAT_S3_*` / `HOUSTON_CHAT_PRIVATE_MEDIA_ROOT`).
  - Reserve + presigned PUT + Houston `complete` (validation + Celery thumbnail for images). Not `TemporaryUpload`.

- `TemporaryUpload`
  - Unlinked file captured before the final Observation submit flow completes.
  - Exists only until it is linked, deleted, or cleaned up.

- `ObservationMedia`
  - Photo media linked to a submitted Observation.
  - Visible only through authorized parent-resource access, not as a public standalone asset.

- `TranscriptionAudio`
  - Temporary audio used only to produce editable transcription text.
  - Must not become persistent Observation media in MVP.

- `MediaMetadata`
  - Safe metadata about the file or lifecycle state.
  - Must not expose raw media content or sensitive payloads.

- `SignedMediaUrl`
  - Implemented as Houston-hosted `preview_url` / `thumbnail_url` with a short-lived signed query token. Authorization is re-checked on each Houston GET before 302 or `FileResponse`.

- `MediaCleanupJob`
  - Implemented as `cleanup_expired_uploads_task` (Celery beat) plus `cleanup_expired_uploads` for expired unlinked `TemporaryUpload` rows and their principal + thumbnail objects.

## 6. Lifecycle / Statuses

`TemporaryUpload.Status` is persisted as `validated` → `linked` on Observation submit, or `deleted` on explicit delete / TTL cleanup. The MVP lifecycle is:

- local selection on the client
- temporary upload created (`validated`)
- backend validation
- normalized and stored, or rejected by backend
- link to Observation on submit (`linked`)
- authorized access through the parent resource
- orphaned or expired `validated` rows cleaned up
- deleted (`deleted`)

For transcription audio, the MVP lifecycle is:

- local recording
- temporary upload or backend-controlled transport
- transcription
- validated text accepted into the Observation flow
- audio deleted

## 7. Permissions

- A user may upload media only inside an authorized establishment context.
- A user may link media only to a resource they are allowed to create or update.
- Viewing media requires visibility of the authorized parent resource.
- Standalone public media access is forbidden.
- Houston-hosted `preview_url` / `thumbnail_url` require backend authorization on each GET before 302 or `FileResponse`.
- Active membership and establishment scoping are mandatory for any media action.
- Cross-tenant media access is forbidden.
- Broad support or admin media access is not a default product behavior and must not be assumed.

## 8. HTTP

[`apps/api/schema.yml`](../../../apps/api/schema.yml) — temporary uploads, transcription, observation-media preview. Chat attachments are a dedicated bucket, not `TemporaryUpload`.

## 9. Frontend Expectations

- Frontend may collect text, photos, and audio for the Observation flow, but backend validation is authoritative.
- Observation photos stay local `File` objects in process memory until Envoyer. `POST …/temporary-uploads/` runs at send, not during compose. Task-origin Observation is text-only compose.
- Frontend should block obvious invalid states early, including photo-only Observation submit attempts and Envoyer while offline.
- Upload/link states after Envoyer starts are not business truth; a failed send must not treat the Observation as created and must keep the local draft.
- Frontend must not assume media is linked until backend confirmation arrives through the API.
- Frontend must not treat upload completion as Observation submit completion.
- Audio should remain local or temporary and must not be stored durably in the browser.
- Sensitive media must not be persisted in durable browser storage.
- TanStack Query owns server state for implemented APIs.
- Frontend must use generated API clients only for endpoints present in `apps/api/schema.yml`.
- Frontend must not guess media URLs or rely on direct public access patterns. Tiles use `thumbnail_url`; the lightbox uses `preview_url`. Both stay on the Houston host.

## 10. Agent notes

- Inspect current upload/media code before claiming models, jobs, or endpoints exist.
- Inspect `apps/api/schema.yml` before listing any upload/media endpoint as implemented.
- Inspect the Observation, AI, Security / RGPD, and RBAC domain docs before changing submission, transcription, privacy, or access behavior.
- Do not invent direct browser-to-storage upload, extra image CDNs, or public bucket URLs in JSON.
- Do not log media content, signed access URLs, tokens, `Location` headers, or sensitive filenames.
- Do not send images to AI in MVP.
- Do not persist transcription audio as Observation media in MVP.
- Do not add media to Chat V1 except through the dedicated chat attachment flow.
- Do not increase the photo limit without updating product docs, backend validation, frontend validation, and tests.
- When upload/media APIs change, update backend authorization, OpenAPI, generated clients, tests, and this document together.
